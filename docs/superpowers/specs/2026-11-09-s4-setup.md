# S4: Setup, key storage, notices, phone guidance and voice

**Date:** 2026-11-09
**Status:** Draft, waiting for the user's review.
**Builds on:** main spec §7 (privacy), §8 (setup) and §9, security spec §2 (T7, T12), §3 and §4, S2 §3 and §9 (`ProviderConfig`, `ProviderCheck`, presets), S3 §8 (the debug-only config that S4 removes) and §9 (manifest).
**Implements:** the `SetupActivity` checklist of main spec §8, Keystore storage of the API key, the first-run notices, restricted-settings guidance, and voice input on the task screen.

## 1. Scope and exit gate

S4 lets a stranger go from installing the APK to a finished first task using only the app's own screens. Today the provider comes from `local.properties` at build time. S4 replaces that with an in-app setup.

**Exit gate:** on the test phone (Nothing A059, Android 16), from a fresh install of a release-style build with no `local.properties` keys, the user completes the setup screen and a test task finishes. No `adb`, no rebuild, no file editing.

**Decisions taken in the design talk (2026-11-09):**

| # | Question | Decision |
|---|---|---|
| 1 | Voice language | The phone's own language setting. No picker in v0.1. Hindi and Hinglish tuning comes after launch. |
| 2 | How far the brand palette goes | Every screen and card in the app (§7). The bubble keeps its state colours, because they carry meaning. |
| 3 | One provider setup or several | One active configuration, edited in place. Each saved configuration carries an id (`default`) so profiles can be added later without redoing storage. |
| 4 | What happens after speaking | The recognised words fill the text box. The user presses Go. |
| 5 | Structure | A pure core in a new platform-free package with thin Android parts (§2). |
| 6 | The debug-only provider path | Deleted: `DevConfig`, the `POCKETAGENT_*` build fields and reading `local.properties` (§3.4). |

**Not in S4:** several provider profiles, a language picker, a Quick Settings tile (v0.2), fetching a model list from the provider, cloud backup of settings, migration from the debug config (nothing has been released), playbook authoring (S5), signing and release (S6).

## 2. Units

The rule from Plans 1 to 3 holds: core packages import no Android types (`ArchitectureTest`). Every decision that can be made without Android lives in plain Kotlin and is tested on the JVM.

**Pure Kotlin, new package `setup/`**

| Unit | Job |
|---|---|
| `SetupFacts` | A plain snapshot of what is true now: notice accepted, the host the user accepted a custom-URL warning for, the saved `ProviderConfig` or none, the last `CheckResult` for that exact config or none, accessibility on, microphone state (`NOT_ASKED`, `GRANTED`, `DENIED`), bubble on, test task finished |
| `SetupStep` | `NOTICE`, `PROVIDER`, `MODEL_CHECK`, `ACCESSIBILITY`, `MICROPHONE` (optional), `BUBBLE`, `TEST_TASK` |
| `SetupModel` | `evaluate(facts)` returns each step as `DONE`, `CURRENT` or `TODO`, each undone step with the earlier step it needs first (or none), and `isReady` (§3.1) |
| `ConfigRepository` | Interface: `load(): ProviderConfig?`, `save(config)`, `clear()`. The Android implementation combines `SettingsStore` and `KeyVault` |
| `SealedValue` | Encodes and decodes the stored form of the key (IV plus ciphertext as one text value); corrupt input decodes to nothing, never throws |
| `SpeechErrors` | Maps `SpeechRecognizer` error codes to short plain messages |
| `GuidanceStore` | Parses and validates the per-phone guidance files (§5.2), strictly, like `PlaybookStore` |

**Android, `android/` and `ui/`**

| Unit | Job |
|---|---|
| `SettingsStore` | Private SharedPreferences for everything that is not secret |
| `KeyVault` | AES-256-GCM with a non-exportable Android Keystore key; stores a `SealedValue` |
| `AndroidConfigRepository` | The `ConfigRepository` implementation |
| `SetupActivity` | Replaces `LauncherActivity`; the single checklist screen (§5), plain Views |
| `VoiceInput` | Wraps `SpeechRecognizer` for the task and answer screens (§6) |
| `TaskInputActivity` | Gains the mic button (§6) |
| `AgentSession` | Reads `ConfigRepository` when a task starts (§3.3); starts the setup test task (§5.1) |

## 3. Setup state and storage

### 3.1 The step model

`SetupModel.evaluate(facts)` is a pure function. Rules:

| Step | Done when |
|---|---|
| `NOTICE` | the notice is accepted |
| `PROVIDER` | a config is saved, `validate()` has no errors, and, if its host is not a preset host, the user accepted the warning for that exact host |
| `MODEL_CHECK` | the last `CheckResult` for the current config is `Works` |
| `ACCESSIBILITY` | the service is enabled |
| `MICROPHONE` | `GRANTED`. Optional: `DENIED` or `NOT_ASKED` never blocks any other step and does not stop `isReady` |
| `BUBBLE` | the bubble flag is on |
| `TEST_TASK` | a setup test task has finished successfully |

The first required step that is not done is `CURRENT`; every later required step is `TODO`. An undone step also carries the earlier step it needs first, used to disable its button and show "Finish *X* first": `MODEL_CHECK` needs `PROVIDER`, and `TEST_TASK` needs `MODEL_CHECK` and `ACCESSIBILITY`. `isReady` is true when every required step is `DONE`.

**Invalidation:** saving a different provider kind, base URL, key or model clears the stored `CheckResult`, and so also `MODEL_CHECK` and `TEST_TASK`. A stale "works" cannot survive an edit. Turning accessibility off afterwards makes `ACCESSIBILITY` current again.

The screen re-evaluates on every `onResume`, because the user comes back from Android Settings and the permission dialog.

### 3.2 Non-secret settings

`SettingsStore` keeps: provider kind, base URL, model, `supportsImages`, the optional token settings with their S2 defaults, the notice-accepted flag, the accepted custom host, the microphone-asked flag, the bubble flag, the test-task-finished flag, and the config id (`default`). The bubble flag defaults to off. Nothing about screens, tasks or the model's replies is stored (S3 §7 is unchanged).

### 3.3 The key

`KeyVault` generates one AES-256 key in the Android Keystore under a fixed alias, non-exportable, with no user-authentication requirement, because the agent runs in the background. For each save it uses a fresh random 12-byte IV, and stores IV plus ciphertext as one text value (`SealedValue`).

- **Failure is never a crash.** A missing key, a tampered value, or a Keystore that was reset decodes to "no key". The setup screen then asks for the key again.
- **No plaintext fallback.** If the phone cannot create a Keystore key, the app refuses to save the key and says so plainly. It never stores the key unencrypted.
- **Display:** after saving, the field shows "Key saved" with a Replace button. No characters are revealed. The key is never logged, never put in a URL, and `ProviderConfig.toString` already masks it.
- **Backup:** `allowBackup="false"` and the data-extraction rules already exclude everything, so the encrypted value never leaves the phone.
- **Use:** `AgentSession` calls `ConfigRepository.load()` each time a task starts, so a changed configuration takes effect without restarting the service. With no valid config, a bubble tap opens `SetupActivity` instead of the task screen.

### 3.4 Removing the debug-only path

Deleted: the `src/debug` and `src/release` `DevConfig` classes and their test, the five `buildConfigField` lines, the `local.properties` reading in `app/build.gradle.kts`, and `buildConfig = true` if nothing else needs it. The two `ArchitectureTest` rules about key build fields are replaced by one: `BuildConfig` has no key, URL or model fields at all. Developers type the key into the app once. `docs/TESTING.md` stops describing `local.properties` keys.

## 4. Notices

The notice text is fixed in `strings.xml` and must say, in plain language:

1. Screen text, and screenshots when the agent asks for one, go directly to the provider the user chose, and nowhere else. No telemetry, no analytics, no backend.
2. Nothing from the screen is stored after a task ends.
3. The agent can tap and type on the phone while a task runs. It asks before actions that may send, pay, post or delete, and it never works in banking, payment, password-manager or Settings apps. This is a heuristic and can miss unusual wording.
4. Any person can stop a running task by long-pressing the bubble.

A **custom base URL** adds a warning naming the real host: "Your screen text will be sent to `<host>`." Accepting it is stored per host, so changing the host asks again. A plain-`http` local server keeps the warning from S2.

The **microphone card** explains that the system speech recogniser may send audio to the phone maker's or Google's service, and that on-device recognition is requested first. These texts are covered by a build-time test (§9).

## 5. The setup screen

`SetupActivity` replaces `LauncherActivity` as the launcher screen and stays the only exported component. It is one scrolling screen of step cards, plain Views. The current step is expanded, finished steps collapse to a one-line summary with an Edit button, later steps are greyed. `FLAG_SECURE` is set for the whole activity, so screenshots and the recent-apps preview cannot show the key field. State is rebuilt from the stores and live checks, so rotation and process death lose nothing.

### 5.1 The cards

1. **Notice.** The text of §4 and an "I understand" button.
2. **Provider and key.** Preset buttons (Anthropic, OpenRouter, OpenAI, Gemini, DeepSeek, Groq, Ollama) from `ProviderPresets`, or Custom. The key field is a password-style field with autofill off. Errors and warnings from `ProviderConfig.validate()` appear next to the field.
3. **Model and test.** A free-text model name (no default, as in S2 §10), the images switch (preset default), and a Test button that runs `ProviderCheck`. The result messages: `Works` ("This model answers and can use tools"), `NoToolCalls` ("This model cannot use tools, so the agent cannot run on it. Pick another model."), `BadKey`, `Unreachable`, `Other(message)` (shown as the provider's short, key-free message, which covers rate limits). A running check can be cancelled; leaving the screen cancels it.
4. **Accessibility.** A button opens Android's accessibility settings. The enabled state is read from the enabled-services setting. If the switch is greyed out, the card shows the phone's **Allow restricted settings** steps from the guidance file (§5.2) and a button to Pocket Agent's app info page.
5. **Microphone (optional).** The §4 explanation, an Allow button that asks for `RECORD_AUDIO`, and a Skip button. This is the only place in the app that asks for the permission.
6. **Bubble.** An on/off switch. It writes the bubble flag; the running `AgentSession` listens for the change and shows or hides the bubble at once.
7. **Test task.** A harmless pre-filled task that needs no particular app, for example "Look at my home screen and name three apps on it". Pressing Run calls `TaskScreenHost.current?.startSetupTask(text)`. The session presses Home, waits for the screen to settle, reads it, and starts the task. The step is done when that task ends successfully. Without a running service the button explains that accessibility must be on first.

When `isReady`, opening the app shows a short "Ready" view with the checklist collapsed and Edit buttons.

### 5.2 Phone guidance

Guidance files live in `assets/guidance/` and are named `<manufacturer>.md`, lower-case, matching `Build.MANUFACTURER`, with `generic.md` as the fallback. Each is plain text for the restricted-settings step and is validated at build time (§9). The files shipped in S4 are `generic.md` and `nothing.md`; the Nothing steps are the ones verified on the test phone. No other brand's steps are written until someone has verified them on a real phone. Other phones can be added by pull request.

## 6. Voice on the task screen

`VoiceInput` wraps `SpeechRecognizer` (an in-process API with no extra screen, so the task screen is not stopped). It is used on the task screen and the answer screen.

- **Language:** no language is set, so the phone's own language is used. On-device recognition is requested first (`EXTRA_PREFER_OFFLINE`), and partial results fill the box as the user speaks.
- **Flow:** tap the mic to listen, tap again to stop. The recognised words stay in the box for the user to edit. The user presses Go. The 2,000-character cap and the empty-text rule are unchanged.
- **Errors** map through `SpeechErrors` to short messages: nothing heard, no connection for the recogniser, recogniser busy, microphone not allowed.
- **No recogniser on the phone:** the mic button is hidden and typing works as today.
- **Permission** is requested only in setup (§5.1 card 5), never from the task screen. The task screen dismisses itself when it stops (S3 §6), and Android's permission dialog is a separate screen that would stop it. If the microphone is not allowed, the button shows a short hint to turn it on in setup.
- **Lifecycle:** one recogniser at a time, destroyed when the screen stops or closes, and cancelled on dismissal. Nothing the user says is logged or kept.

## 7. Brand palette

Applied to every screen and card: setup, the task and answer screens, the confirmation card, the summary card and the caption. The bubble keeps its state colours (grey, blue, amber, green, red), because they carry meaning and the palette has no green or red; the running ring uses the brand blue.

| Token | Value | Use |
|---|---|---|
| Background (midnight black) | `#090A10` | screen and overlay backgrounds |
| Surface | `#121520` | cards |
| Border | `#1E2333` | card borders, dividers |
| Blue | `#1E6FFF` | step state, links, focus, icons, secondary buttons |
| Blue, subdued | `#1A2B4C` | selected and highlighted fills |
| Orange | `#FF8544` | the main action button, the current-step marker |
| Text | `#F8F9FC` | primary text |
| Muted text | `#8E95A5` | secondary text |

**60-30-10:** about 60% of the pixels are midnight black and surfaces, about 30% blue and its subdued fill, about 10% orange.

**Contrast rules** (checked against the values above):

- Dark text on orange is about 8:1, so orange buttons use dark text.
- Off-white text on solid blue is about 4.2:1, slightly under the 4.5:1 minimum for small text. Labels on solid blue are bold and at least 18 sp.
- Blue is used for fills, borders, icons and large text, not for small body text, because blue on a surface is about 4.1:1.
- Muted grey on black or on a surface is about 6:1 and is fine for secondary text.
- On the confirmation card, Allow and Decline have the same size and weight, and the colours are chosen so that Allow is not more prominent than Decline.

## 8. Manifest and permissions

Unchanged: the permissions stay `INTERNET` and `RECORD_AUDIO`; no overlay permission; no `QUERY_ALL_PACKAGES`; `allowBackup="false"` and the data-extraction rules stay; the only exported component is the launcher. `LauncherActivity` is renamed `SetupActivity` and keeps the launcher intent filter. `manifestMatchesAllowlist` passes unchanged.

## 9. Testing

**JVM tests (CI):**

- `SetupModel`: every step transition, including accessibility switched off after setup, a key edited after a passed check, a denied microphone, a custom host accepted and then changed, and the "needs X first" hints.
- `SealedValue`: round trip, and corrupt, empty and truncated input.
- `ConfigRepository`: its contract against a fake (save, load, clear; key missing means no config; an edit clears the check).
- `SpeechErrors`: every code maps to a non-blank message.
- Build-time validation of the notice texts and the guidance files: size limit, no control characters, correct file names, a `generic.md` present.

**New `ArchitectureTest` rules:** `setup` imports no Android; `BuildConfig` has no key, URL or model fields; `SetupActivity` is the only exported component; `RECORD_AUDIO` is requested only in setup code; `SetupActivity` sets `FLAG_SECURE`; permissions stay `INTERNET` and `RECORD_AUDIO`; no `androidx`.

**On the phone** (added to the device checklist in `docs/TESTING.md`, the same way as S3):

1. The exit gate: fresh install, no `local.properties` keys, setup to a finished test task.
2. The key survives the app being killed. Clearing the app's data makes setup ask again.
3. The restricted-settings steps work on the Nothing phone.
4. Bad key, a model with no tool calls, and an unreachable server each show a clear message. A rate limit shows the provider's message.
5. Microphone: granted, denied, and without a connection.
6. A screenshot of the key field is blocked.
7. Toggling accessibility updates the checklist.
8. A custom URL shows its real host in the warning.
9. The palette: all screens and cards are readable, and the Allow and Decline buttons are equally prominent.

## 10. Risks

| Risk | Handling |
|---|---|
| Keystore behaviour differs between phone makers and some fail to create a key | The app refuses to save the key and says why. There is never a plaintext fallback (§3.3). |
| The user pastes a key into a provider's wrong field | The check returns `BadKey` with a clear message; the key is masked in the UI. |
| Recognition quality in Hindi depends on the phone | Out of scope for v0.1 (decision 1); noted in the README. |
| Guidance for other phone makers is missing | `generic.md` is the fallback and others are added when verified on a real phone. |
| Rate limits on free models look like an app fault | The `Other` message from the provider is shown on the model card. |
